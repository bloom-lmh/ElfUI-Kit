# ElfUI v0.0.2-beta.1 代码架构、封装与 beta.12 模板计划

日期：2026-07-28

状态：执行中

约束：功能、公开 API 和视觉行为默认不变

## 1. 目标

本计划不以“减少行数”为唯一目标，而是降低组件的认知负担、重复实现和副作用风险：

- 状态集中、派生值集中、方法集中。
- 模板只表达结构，不承载复杂业务判断。
- 纯算法与 DOM 副作用分离。
- 复用 ElfUI Core 已提供的组合式函数。
- 仅在模板本身构成认知负担时使用 beta.12 Fragment；Fragment 不是主要重构指标。
- 避免为了封装而制造大量难以追踪的抽象层。

当前优先对象：

| 组件 | 当前规模（约） | 主要问题 |
| --- | ---: | --- |
| Table | 2750 行 | 列模型、选择、排序、虚拟化、浮层和模板集中 |
| Cascader | 1473 行 | 路径状态、异步、键盘、列模式和树模式耦合 |
| Menu | 1216 行 | 模型、折叠、嵌套浮层和选中反馈耦合 |
| Tree | 1104 行 | 规范化、勾选、虚拟、懒加载和拖拽耦合 |
| Dropdown | 926 行 | 定位、焦点、菜单状态和模板重复 |
| DatePicker | 768 行 | 输入状态、范围状态、面板和定位耦合 |
| Tabs / Upload | 746 行 | 交互状态与大模板集中 |

行数只用于发现风险，不作为机械拆分指标。

## 2. 顶层架构原则

ElfUI Kit 后续按能力分层，而不是按组件名称复制实现：

```text
公开类型与能力协议
  → 无界面 service / 纯算法
    → Provider / composable 适配器
      → 内部交互基元
        → 公开组件
          → 文档案例与契约测试
```

强制约束：

1. **依赖抽象**：组件依赖 `GoTo`、Overlay controller、Field state、Collection model 等协议，不依赖另一个公开组件的内部实现。
2. **高内聚**：业务状态机留在所属组件；跨组件重复的容器解析、资源协调、几何计算和策略选择进入能力层。
3. **低耦合**：无界面 service 不读取 host、Provider 或全局可变单例；Provider 通过适配器注入默认策略。
4. **开放扩展、关闭修改**：缓动、日期、图标、字段、主题等变化通过策略、适配器和配置扩展，避免为每个新需求修改所有组件。
5. **组合优于继承**：共享行为采用纯函数、controller 和 composable；共享外观采用语义 token、状态映射和必要的内部 Field shell。
6. **单一权威实现**：滚动、overlay、virtual window、collection navigation 等能力只能有一个底层实现。
7. **可替换、可测试**：抽象必须有明确输入、输出、取消与清理语义；纯逻辑测试和组件契约测试分开。

采用的设计模式必须服务于真实变化点：

- Strategy：滚动 easing、日期 adapter、字段解析、过滤和排序。
- Adapter：ConfigProvider、外部 i18n、图标集和宿主框架集成。
- Controller：overlay、drag transaction、programmatic scrolling。
- State machine：Picker 范围选择、Cascader 异步路径、Upload 生命周期。
- Registry：overlay stack、collection items、组件 metadata。

禁止建立“万能 composable”或把所有组件强行塞进同一 DOM 基元。抽象出现前必须先确认语义相同，而不只是代码长得相似。

## 4. 五种封装方式的边界

选择顺序是：纯函数 / service → composable / controller → 公共样式协议 → 内部组件 → Fragment。Fragment 只解决同文件模板表达，不解决跨组件行为复用。

### 4.1 纯函数或无界面 service

适用：

- 数据规范化、索引、过滤、排序、范围与几何计算。
- 可取消任务、平台能力封装和独立于渲染层的策略执行。
- 与 DOM 无关的状态转换，或把 DOM 作为显式参数而不持有组件状态的服务。

### 4.2 composable / controller

适用：

- 需要绑定组件生命周期、Provider 配置或资源清理的行为。
- 需要把通用 service 适配到当前组件上下文，但不拥有组件业务状态机。

### 4.3 公共样式协议与内部组件

优先共享语义 token、CSS custom properties、状态映射和纯样式片段。只有多个组件确实共享 DOM、交互生命周期和无障碍语义时，才建立内部组件。

### 4.4 `fragment`

适用：

- 一次性的短小局部模板。
- 不需要命名复用的静态结构。
- 不发生重排、无需稳定 key 的简单 `array.map()` 展示。

不适用：

- 可排序、可插入、可删除的交互列表。
- 含独立生命周期或跨文件复用的结构。
- 运行时动态模板。

对于可重排列表继续使用带稳定 key 的 `v-for`。

### 4.5 `defineFragment<Props>()`

适用：

- 同一个组件文件内需要命名的模板区域。
- Header、BodyRow、Empty、Tags、Panel 等纯展示区域。
- 通过只读 props 消费外层状态与方法的结构。

特性与约束：

- 编译期透明，不注册 Custom Element。
- 不创建 Shadow Root，不拥有生命周期。
- 必须是当前文件局部常量，不能 export 或跨文件使用。
- 不在 Fragment 内隐藏业务状态机。

### 4.6 纯函数或逻辑模块（兼容原计划）

适用：

- 数据规范化、索引、过滤、排序、范围计算。
- 与 DOM 无关的状态转换。
- 独立可测试或被三个以上调用点复用的逻辑。

示例：

```ts
normalizeColumns(input)
deriveCheckedState(tree, keys)
resolveCascaderPath(options, value)
calculateVirtualRange(viewport, itemSize)
```

纯逻辑不得读取组件 host、document、window 或模块级可变单例。

### 4.7 真实内部组件 `defineHtml()`

仅在满足至少一个条件时使用：

- 需要跨文件复用或独立公开。
- 需要独立生命周期、Shadow Root、slot 或 form-associated 行为。
- 是可独立测试和理解的交互单元。
- 需要独立注册或公开 API。

不要把每个模板片段都变成 Custom Element，否则会增加 DOM 层级、事件边界和调试成本。

## 5. 统一文件结构

宏组件优先按以下顺序组织：

```ts
// 1. imports
// 2. public types
// 3. props / emits / slots / options
// 4. constants and injected contexts
// 5. state
// 6. derived state
// 7. lifecycle-bound composables
// 8. methods grouped by responsibility
// 9. named fragments
// 10. styles
// 11. root template
// 12. exports
```

方法按责任分组，而不是按调用顺序散落：

```ts
// value synchronization
// selection
// keyboard
// overlay
// form integration
// public methods
```

## 6. Core 能力采用计划

beta.12 已提供以下能力，ElfUI Kit 不应继续平行维护同义实现：

- `useEventListener`
- `useClickOutside`
- `useEscapeKey`
- `useScrollLock`
- `useFocusTrap`
- `useResizeObserver`
- `useIntersectionObserver`
- `useFormControlContext`

迁移步骤：

1. 记录现有 Common helper 的行为差异。
2. 为 Shadow DOM composed path、嵌套 overlay、卸载清理建立特征测试。
3. 能直接替代的调用点迁移至 Core。
4. Kit 只保留组件库层的协调逻辑，例如 overlay stack，不复制基础监听器。
5. 删除旧 helper 前运行所有引用扫描和浏览器回归。

注意：`components/Common/anchored-overlay.ts` 的定位计算仍属于组件库能力；Core 的点击外部、Escape 和焦点函数不能替代完整的 overlay 协调器。

### 7.2 Field shell

提取 Input、Select、Autocomplete、Cascader、ColorPicker、DatePicker、TimePicker 共同的字段外观协议：

- label、placeholder、prefix/suffix、clear。
- variant、size、disabled、readonly、invalid、loading。
- focus ring、图标对齐、浮动 label 和多行高度。
- CSS custom properties 和 parts。

实现方式优先为共享样式 token、类型和纯状态函数；只有需要共享真实交互生命周期时才增加内部组件。

### 7.3 Collection model

为 Select、Menu、Tabs、Tree 等整理统一概念：

- active：键盘当前项。
- selected：已选择项。
- disabled：不可交互项。
- roving tabindex：单一 Tab 停靠点。
- typeahead：字符搜索。

各组件保留各自 ARIA role 和选择语义，不使用一个过度泛化的万能类。

### 7.4 Virtual window

以现有 `Data/virtual-window.ts` 为唯一基础：

- 固定高度范围计算。
- overscan。
- scrollToIndex。
- 数据变化后的锚点恢复。

动态高度作为独立扩展，不把未成熟实现塞进所有组件。

## 8. 复杂组件分批重构

### 8.1 Table

逻辑模块：

- `column-model.ts`：列规范化、固定列和可见列。
- `row-model.ts`：row key、树形展开和扁平化。
- `selection.ts`：单选、多选、全选和禁用。
- `sort-filter.ts`：本地状态与受控事件。
- `virtualization.ts`：范围、overscan 和滚动锚点。
- `resize.ts`：列宽、拖拽和边界。

同文件 Fragment 候选：

- `HeaderRow`
- `BodyRow`
- `EmptyState`
- `LoadingState`
- `FilterPanel`

验收：

- 排序不依赖滚动后才刷新。
- 选择、固定列、tooltip 和虚拟滚动回归通过。
- 纯逻辑模块不操作 DOM。
- 根模板能够从上到下读懂结构。

### 8.2 Cascader

逻辑模块：

- options 规范化和字段映射。
- value/path 双向映射。
- 单选、多选和父子状态。
- lazy/async 加载状态。
- columns/tree 两种视图投影。
- 键盘导航。

Fragment 候选：

- `Trigger`
- `TagList`
- `ColumnPanel`
- `TreePanel`
- `EmptyState`
- `Footer`

要求：

- 超过三级的树化只是视图策略，不能改变选择模型。
- 深层节点展开不因重复点击父节点而错误折叠。
- async 竞态、失效请求和卸载后回调有测试。

### 8.3 Menu / Dropdown

抽离：

- item registry 和路径索引。
- active/selected/opened 状态。
- collapse 和响应式投影。
- keyboard/typeahead。
- submenu overlay 协调。

Fragment 用于顶层项、分组、折叠提示和空态，递归菜单仍保持稳定 key。

### 8.4 Tree

抽离：

- 节点规范化与索引。
- 展开、选择、勾选传播。
- lazy load。
- virtual flatten。
- drag transaction 与合法目标判断。

拖拽过程拆成：

```text
pointer/keyboard intent
→ candidate target
→ allowDrop validation
→ visual indicator
→ immutable reorder result
→ change event
```

### 8.5 Picker

DatePicker、TimePicker、ColorPicker 共用 Field shell 和 Overlay 协议，但面板状态分别维护。

DatePicker 抽离：

- 日期算术与 adapter。
- 单值/范围选择状态机。
- calendar grid 投影。
- format/parse。

Fragment 用于 InputTrigger、Header、CalendarGrid、QuickActions 和 Footer。

## 9. 样式封装计划

### 9.1 Token 层

统一语义 token：

- field surface/border/focus/label/icon。
- overlay surface/elevation/radius/z-index。
- state hover/active/selected/disabled/error。
- density、spacing、typography、motion。

### 9.2 组件层

- 每个 Shadow Root 内继续定义组件样式。
- 共享变量名和 mixin，不用全局选择器穿透内部节点。
- 对外只承诺文档化的 CSS custom properties 与 `::part()`。
- 禁止为了少写几行 CSS 而打破 Shadow DOM 封装。

### 9.3 清理规则

- 合并完全相同且语义一致的声明。
- 相似但语义不同的状态不强行共用选择器。
- 删除重复 magic number，转为语义 token。
- 视觉回归前不做批量格式化式重写。

## 10. API 与元数据自动化

建立从组件声明到交付物的单一元数据流水线：

```text
defineProps / defineEmits / defineSlots / defineExpose / defineOptions
→ component metadata
→ HTMLElement 类型
→ API 文档 JSON
→ 注册清单
→ 单组件 exports
→ ConfigProvider defaults 类型
```

目标：

- 减少 Props 表格、类型和实现不同步。
- 为 resolver、aliases 和按需导入提供可靠数据源。
- CI 检查公开组件是否缺少 API 文档、测试或案例。

## 11. 测试与截图策略

每个重构组件按顺序执行：

1. 重构前保存关键案例截图和性能数据。
2. 补齐缺失的行为特征测试。
3. 一次只移动一个责任边界。
4. 运行纯逻辑、组件和页面测试。
5. 在真实浏览器验证 light/dark、键盘、RTL 和窄屏。
6. 对比截图，不接受“测试通过但布局改变”。
7. 完成一个组件后独立提交，便于回滚和审查。

Table、Tree、Select 的性能至少记录：

- 首次渲染 DOM 节点数。
- 选择/排序/过滤的更新时间。
- 滚动期间长任务和掉帧。
- 数据替换后的内存与监听器清理。

## 12. 禁止事项

- 不在模块顶层保存跨实例可变状态。
- 不把所有组件行为塞进一个通用 composable。
- 不让 Fragment 拥有隐藏状态或充当跨文件组件。
- 不用 index 作为可重排列表身份。
- 不在模板中重复执行昂贵过滤、排序或路径查找。
- 不因“代码更短”牺牲类型、ARIA、错误边界或可调试性。
- 不在没有特征测试时删除现有兼容分支。

## 14. 完成定义

代码优化完成不等于文件变短，而是满足：

- 公开行为和视觉无意外变化。
- 状态与方法有清晰分组。
- 模板能够快速读出主结构。
- 纯逻辑可独立测试。
- 副作用由生命周期绑定的 API 管理。
- 共享能力只有一个权威实现。
- 复杂组件不再同时承担数据模型、DOM 副作用和全部模板细节。
- typecheck、全量测试、build、浏览器交互和截图验证全部通过。

## 15. Fragment 文档依据

本计划采用 ElfUI beta.12 的：

- `fragment\`...\``：匿名、一次性、编译期局部模板。
- `defineFragment<Props>()`：同文件、命名、带类型的局部模板。

两者都不会注册 Custom Element、创建 Shadow Root 或拥有生命周期；跨文件复用和独立交互单元继续使用 `defineHtml()`。
